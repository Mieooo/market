# 大模型求职与研究雷达：前端优先 MVP 技术方案

## 1. 文档目的

本文档定义 MVP 的前端架构、Mock 数据方案、页面与交互、视觉设计系统、质量标准，以及后续接入真实数据的迁移方式。

产品范围和业务验收以 `docs/PRODUCT.md` 为准。本文档重点解决“如何实现”。

## 2. 阶段目标

### 2.1 第一阶段：前端原型 MVP

第一阶段只验证产品表达与操作逻辑：

- 用户能否快速理解产品价值；
- 用户能否发现正在变化的行业难题；
- 用户能否从趋势下钻到证据；
- 求职和作品集建议是否有行动价值；
- 动态问题、筛选和详情结构是否自然；
- 视觉是否达到高级、简约、有动态感的目标。

数据使用结构完整、分布合理的 Mock 数据。第一阶段不要求联网抓取，不要求真实趋势结论，也不建设后台管理系统。

### 2.2 第二阶段：真实数据接入

第二阶段保留页面组件与数据契约，替换数据提供层：

- Mock Repository 替换为 HTTP API Repository；
- 接入现有 FastAPI、SQLite 和数据管线；
- 增加真实的抓取批次、证据验证与趋势计算；
- 增加错误恢复、缓存和数据新鲜度提示；
- 逐步将种子问题迁移为动态发现的问题。

两阶段之间不应重写页面。前端组件只能依赖统一领域类型和查询接口，不能直接依赖 Mock JSON 的文件结构。

## 3. 总体技术决策

### 3.1 前端技术栈

| 领域 | 选择 | 用途 |
| --- | --- | --- |
| UI 框架 | React + TypeScript | 页面、组件和交互状态 |
| 构建工具 | Vite | 快速开发、静态构建和当前托管兼容 |
| 路由 | React Router | 首页、问题详情、证据库等独立 URL |
| 样式 | CSS Modules + 全局 Design Tokens | 保持视觉独立性，避免套模板感 |
| 动效 | CSS Transition + Motion for React | 状态变化、列表重排和页面过渡 |
| 图表 | Apache ECharts，按需导入 | 趋势线、构成图和时间分布 |
| 数据校验 | TypeScript 类型 + Zod | Mock 与真实 API 的运行时契约校验 |
| 单元测试 | Vitest + Testing Library | 数据映射、评分展示和组件行为 |
| 端到端测试 | Playwright | 核心浏览、筛选和下钻流程 |
| 后端保留 | FastAPI + SQLite | 第二阶段数据服务，不参与首期页面开发 |

不在 MVP 中引入 Next.js、服务端渲染、状态管理大框架或完整 UI 组件库。当前目标是静态部署和交互验证；如果后续公开内容增长且 SEO 成为核心获客渠道，再评估 SSG/SSR。

### 3.2 为什么不继续使用单文件 HTML

现有 `dist/index.html` 已能展示概念，但页面、样式、数据读取和交互全部耦合在一个文件中，并且存在固定的问题枚举和推荐规则。

新版本需要支持动态路由、加载状态、列表重排、复杂筛选、Mock/真实 API 切换和视觉组件复用，因此应迁移为组件化前端。原页面只作为数据口径和已有功能参考，不在其上继续堆叠逻辑。

### 3.3 不采用通用 UI 模板

不直接使用 Ant Design、Material UI 等完整视觉体系。它们可以提高后台开发速度，但容易形成通用管理后台观感，不符合本产品“研究刊物 + 情报终端”的品牌方向。

基础可访问行为可以借鉴无样式组件思想，但色彩、字体、间距、边框、卡片、图表和动效必须由本项目的 Design Tokens 控制。

## 5. 数据契约优先架构

### 5.1 Repository 接口

页面不直接 `fetch` JSON，而是通过统一接口读取数据：

```ts
export interface RadarRepository {
  getOverview(query: OverviewQuery): Promise<Overview>;
  getProblems(query: ProblemQuery): Promise<ProblemSummary[]>;
  getProblem(id: string): Promise<ProblemDetail>;
  getSignals(query: SignalQuery): Promise<SignalPage>;
  getEvidence(query: EvidenceQuery): Promise<EvidencePage>;
  getMethodology(): Promise<Methodology>;
}
```

第一阶段由 `MockRadarRepository` 实现，第二阶段由 `ApiRadarRepository` 实现。通过环境变量切换：

```text
VITE_DATA_MODE=mock
VITE_DATA_MODE=api
```

### 5.2 Mock 不只是静态假数字

Mock 数据必须模拟真实产品行为，至少包括：

- 8 至 12 个动态问题，而不是固定五类；
- 40 至 60 条证据；
- 最近 12 周的趋势序列；
- 招聘、工程实践、研究、行业报告等来源类型；
- 新出现、升温、稳定、降温、归档状态；
- 高、中、低置信度；
- 多地区、多行业、多岗位和技能；
- 可验证、仅线索、抓取失败三类证据；
- 问题别名、相关问题和合并历史样例。

Mock 数据要保持字段之间逻辑一致。例如问题的证据数量、发布者数量、趋势曲线和详情页列表必须能互相核对，不能为不同页面分别手填互相矛盾的数字。

### 5.3 Mock 场景

除了默认数据，还应支持以下场景，用查询参数或开发面板切换：

```text
?scenario=default
?scenario=loading
?scenario=empty
?scenario=partial
?scenario=stale
?scenario=error
```

这样可以在没有后端的阶段验证骨架屏、空状态、部分数据、过期数据和加载失败，而不是等接入 API 后再补异常界面。

### 5.4 核心前端类型

```ts
type TrendState = "new" | "rising" | "steady" | "falling" | "archived";
type Confidence = "high" | "medium" | "low";
type EvidenceStatus = "verified" | "lead_only" | "failed";

interface ProblemSummary {
  id: string;
  name: string;
  definition: string;
  trendState: TrendState;
  trendScore: number;
  confidence: Confidence;
  firstSeenAt: string;
  lastSeenAt: string;
  evidenceCount: number;
  publisherCount: number;
  industries: string[];
  roles: string[];
  skills: string[];
  history: Array<{ date: string; score: number }>;
}
```

所有外部数据进入 UI 前必须经过 Schema 校验和适配。字段缺失时由适配层提供明确降级结果，组件内部不散落兼容判断。

## 6. 信息架构与路由

### 6.1 `/` 首页

首页负责在 30 秒内回答“这个网站有什么用”和“本周最值得关注什么”。

首屏结构：

1. 一句产品价值主张；
2. 本周最重要的一条动态判断；
3. 三个变化最大的动态问题；
4. 数据截至时间和样本状态；
5. 进入完整雷达和证据库的入口。

首屏之后依次展示：

- 12 周问题趋势；
- 最新招聘与行业信号时间流；
- AI Native 与传统行业 AI 的样本分布；
- 针对程序员的本周行动建议；
- 数据方法和来源透明度。

### 6.2 `/problems` 动态难题

- 默认按趋势变化和置信度综合排序；
- 支持时间、行业、地区、岗位、来源类型筛选；
- 支持列表视图和趋势矩阵视图；
- 筛选条件写入 URL，刷新和分享后仍能恢复；
- 问题卡片只显示决策需要的信息，不堆满标签。

趋势矩阵建议使用两个轴：

- 横轴：证据增长速度；
- 纵轴：证据置信度；
- 点大小：独立发布者数量；
- 颜色：趋势状态。

不使用装饰性雷达图表示单一得分，避免“雷达”名称反过来限制真实的数据表达。

### 6.3 `/problems/:id` 难题详情

详情页按认知顺序组织：

1. 这是什么问题；
2. 为什么现在值得关注；
3. 趋势是如何形成的；
4. 哪些岗位和行业在需要它；
5. 原始证据是什么；
6. 程序员可以采取什么行动。

关键交互：

- 时间窗口切换后趋势图和证据同步更新；
- 点击图表节点过滤对应时间段证据；
- 点击“查看依据”从右侧打开证据抽屉；
- 事实、系统推断和行动建议使用不同视觉标识；
- 相关问题之间可以平滑切换，保留筛选上下文。

### 6.4 `/signals` 求职快讯

- 以时间流展示招聘、报告、工程实践和研究信号；
- 允许切换“全部、招聘、生产实践、研究、政策”；
- 每条信号展示它影响了哪些动态问题；
- 同一事件的转载应聚合成一条，权威原始来源优先；
- 支持查看“本周新增”和“相较上周变化”。

### 6.5 `/evidence` 证据库

- 支持搜索、组合筛选和排序；
- 表格与卡片视图响应式切换；
- 清楚显示证据验证状态和权威等级；
- 外部链接新窗口打开，并使用安全的 `rel` 属性；
- 证据片段和系统总结分开展示。

### 6.6 `/method` 数据方法

用可视化流程说明采集、验证、抽取、聚类、评分和建议生成，公开样本边界和误差来源。该页面既服务用户信任，也作为开发团队的数据口径说明。

## 7. 视觉设计方向

### 7.1 设计概念

整体方向定义为：

> 编辑型研究刊物的可信感 + 数据情报终端的效率 + AI 产品的轻微未来感。

“高级”不依赖大量渐变、玻璃拟态或悬浮卡片，而来自稳定的网格、克制的色彩、优秀的字体层级、细致的数据排版和连贯的交互反馈。

### 7.2 视觉参考

- [Linear](https://linear.app/plan)：参考其高密度信息下的留白、细边框、层级排版、模块化 Dashboard 和精细 Hover；不照搬紫色品牌渐变。
- [Vercel Observability](https://vercel.com/products/observability)：参考“总览指标 → 异常发现 → 一键下钻”的数据产品路径，以及黑白主色中的图表层级。
- [Raycast](https://www.raycast.com/)：参考暗色界面、快捷操作、克制光效和顺滑微交互；不使用大面积玻璃效果。

参考的目标是建立设计语言，不复制布局、插画、Logo 或具体组件。

### 7.3 色彩系统

首版采用中性暗色为主、浅色内容面为辅：

```css
--canvas: #090b10;
--surface-1: #0f1219;
--surface-2: #151923;
--paper: #f5f3ee;
--ink: #111318;
--text-primary: #f4f6f8;
--text-secondary: #9ba3b0;
--line: rgba(255, 255, 255, 0.10);
--accent: #8b7cff;
--signal-cyan: #54d6d0;
--signal-amber: #f2b563;
--danger: #ff6b6b;
```

强调色只用于选择、趋势变化和关键行动。高置信度不能简单等同绿色，避免让“置信”看起来像“结论正确”。图表颜色同时配合形状、线型和文字，不只靠颜色区分。

### 7.4 字体和数字

- 中文优先使用系统无衬线字体栈，避免首期加载大型中文 Web Font；
- 英文与数字优先使用 Inter、Geist 或系统字体；
- 关键数据使用等宽数字特性 `font-variant-numeric: tabular-nums`；
- 大标题紧凑，正文保持舒适行高；
- 标签字号不小于 12px，正文不小于 14px；
- 不用全大写英文充当大量装饰。

### 7.5 网格和组件形态

- 桌面内容最大宽度约 1440px；
- 12 列响应式网格；
- 主要间距基于 4px 倍数，常用 8、12、16、24、32、48；
- 卡片圆角保持 10 至 16px，不使用过度圆润的“玩具感”组件；
- 阴影非常克制，层级主要通过背景差、边框和模糊光晕表达；
- 数据图表与正文共享同一排版基线。

### 7.6 图表设计

首期只使用能帮助决策的图表：

- 多序列趋势折线：观察问题升温和降温；
- 趋势矩阵散点：比较增长速度和置信度；
- 堆叠条形图：查看来源、行业或岗位构成；
- 小型 Sparkline：在列表中表达最近变化；
- 时间流：展示新证据如何推动问题变化。

每张图必须包含口径、时间窗口、样本量和可访问的文字摘要。Tooltip 不能承载唯一信息。

## 8. 动效设计

### 8.1 动效目的

动效只承担四类功能：

1. 解释数据更新和位置变化；
2. 维持从列表到详情的空间关系；
3. 反馈点击、筛选和加载状态；
4. 营造轻微的“持续扫描和发现”感。

禁止无意义的常驻粒子、持续旋转背景、大面积视差和影响阅读的文字逐字动画。

### 8.2 动效规范

- 按钮和 Hover：120–180ms；
- 筛选与卡片重排：180–260ms；
- 页面和详情抽屉：260–420ms；
- 图表初次绘制：400–700ms；
- 默认使用 `transform` 和 `opacity`；
- 列表重排使用布局动画，避免元素瞬移；
- 数据变化时只强调变化的数字或曲线，不重播整页动画；
- 支持 `prefers-reduced-motion`，关闭非必要动画；
- 页面切换时不使用超过 12px 的大幅位移。

### 8.3 标志性动效

首页可以保留一个克制的“信号扫描”动效：细线在趋势图时间轴上缓慢扫过，新证据节点短暂增强亮度后恢复。它应在数秒后停止或降低频率，不影响滚动和阅读。

## 9. 响应式和可访问性

### 9.1 断点策略

- 大屏：1200px 以上，多列数据总览；
- 中屏：768–1199px，双列或主辅布局；
- 移动端：767px 以下，单列、底部筛选抽屉和卡片式证据列表。

移动端不是把桌面页面缩小。复杂图表在移动端应简化序列、支持横向滑动或提供文字摘要。

### 9.2 可访问要求

- 所有交互可用键盘完成；
- 焦点状态清晰且不被移除；
- 正文和关键控件达到 WCAG AA 对比度；
- 图表提供可读取摘要或数据表；
- 状态不能只通过颜色表达；
- 抽屉和弹窗正确管理焦点；
- 支持减少动效设置；
- 页面标题和主要区域使用语义化结构。

## 10. 前端状态管理

MVP 优先使用：

- URL Search Params：可分享的筛选和时间窗口；
- React 局部状态：抽屉、Hover、展开收起；
- Repository 查询缓存：页面数据；
- Context：主题和数据模式等少量全局配置。

没有跨页面复杂写入流程前，不引入 Redux 等全局状态库。

页面需要统一处理六种状态：初始化、加载、成功、空数据、部分失败、完全失败。骨架屏的形状应接近最终内容，避免加载完成后大幅跳动。

## 11. 第二阶段 API 设计

真实数据接入时使用版本化接口：

```text
GET /api/v1/overview
GET /api/v1/problems
GET /api/v1/problems/{id}
GET /api/v1/signals
GET /api/v1/evidence
GET /api/v1/methodology
GET /api/v1/meta/runs/latest
```

列表接口统一支持：

- `from`、`to` 时间窗口；
- `region`、`industry`、`role`、`source_type` 筛选；
- `sort`；
- `cursor` 和 `limit`；
- `q` 搜索。

响应包含：

```json
{
  "data": [],
  "meta": {
    "generatedAt": "2026-09-12T10:00:00+08:00",
    "sampleSize": 60,
    "runId": "run_xxx",
    "isStale": false,
    "nextCursor": null
  }
}
```

前端不展示自己计算出的市场统计。趋势得分、样本量和置信度由后端管线计算，前端只负责验证、格式化和表达。

## 12. 性能方案

MVP 目标：

- 首屏压缩资源不超过约 350KB，不含按需图表模块；
- 非首页路由和复杂图表懒加载；
- ECharts 只导入使用到的图表和组件；
- 图表进入视口后再初始化；
- 列表超过约 200 条时采用分页，暂不默认引入虚拟滚动；
- 图片使用现代格式并声明尺寸；
- 字体首期使用系统栈，避免阻塞首屏；
- 动画保持合成层友好，不持续占用主线程。

质量目标以真实测试为准：

- Lighthouse Performance ≥ 90；
- Accessibility ≥ 95；
- 桌面和主流移动设备无明显布局偏移；
- 低性能设备开启减少动效后可顺畅使用。

## 13. 测试方案

### 13.1 单元测试

- Schema 对正常和异常数据的校验；
- Repository 的筛选、分页和错误模拟；
- 趋势状态、日期和数字格式化；
- 权威等级、置信度和证据状态展示；
- URL 参数与筛选状态同步。

### 13.2 组件测试

- 动态问题卡片在缺失可选字段时仍可用；
- 筛选后列表和统计同步变化；
- 证据抽屉能打开、关闭并恢复焦点；
- 空状态、错误状态和过期状态准确展示；
- 减少动效模式不会依赖动画完成业务逻辑。

### 13.3 端到端测试

至少覆盖：

1. 首页进入动态难题详情；
2. 切换时间窗口并从图表下钻证据；
3. 在证据库组合筛选并清空条件；
4. 从求职快讯打开关联问题；
5. 刷新后恢复 URL 中的筛选状态；
6. 手机尺寸下打开筛选抽屉；
7. Mock 错误场景显示可恢复操作。

端到端测试同时保留关键页面截图，用于发现视觉回归。

## 14. 安全与内容边界

即使第一阶段是 Mock 数据，也按真实外部数据的安全要求实现：

- 来源文本按不可信内容处理；
- 不使用来源 HTML 直接注入页面；
- 不使用未经清洗的 `dangerouslySetInnerHTML`；
- 外链限制为 `http` 和 `https`；
- 外链使用 `noopener noreferrer`；
- 系统推断与来源原文分开展示；
- Mock 内容不得伪装为当前真实市场结论，页面显著标记“演示数据”。

## 15. 开发阶段与交付物

### 阶段 A：视觉基础与工程骨架

- 初始化 React + TypeScript + Vite；
- 建立路由、Design Tokens 和响应式 Shell；
- 实现 Mock Repository 和 Schema；
- 完成首页视觉方向稿；
- 验证桌面和移动端基础布局。

验收：能静态构建和部署，首页在 Mock 模式下完整展示，视觉方向得到确认。

### 阶段 B：核心浏览闭环

- 完成动态难题列表；
- 完成难题详情；
- 完成趋势图和证据抽屉；
- 完成筛选与 URL 同步；
- 完成求职快讯时间流。

验收：用户可以从首页发现问题，在两次点击内到达原始证据。

### 阶段 C：证据透明与质量

- 完成证据库和数据方法页；
- 补齐加载、空、失败和过期状态；
- 增加可访问性、响应式和视觉回归测试；
- 优化包体、图表和动效性能。

验收：通过 MVP 核心端到端测试，达到性能和可访问性目标。

### 阶段 D：真实数据切换

- 实现 `ApiRadarRepository`；
- 对接版本化 FastAPI 接口；
- 迁移真实问题、证据和运行批次；
- 对照 Mock 契约完成集成测试；
- 上线前移除默认演示数据标识。

验收：切换 `VITE_DATA_MODE` 后无需修改页面组件即可使用真实 API。

## 16. 第一阶段不做的事情

- 不开发真实采集器和自动聚类；
- 不把 Mock 趋势对外宣传为真实行业结论；
- 不开发登录、收藏、订阅和付费；
- 不开发简历生成和职位投递；
- 不实现复杂个性化推荐算法；
- 不为了“动态感”加入影响阅读与性能的装饰动画；
- 不提前建设微服务、消息队列或复杂云基础设施。

## 17. MVP 技术验收清单

- 页面中不存在固定五类问题的前端枚举；
- 新增一条符合 Schema 的问题数据即可出现在列表、图表和筛选中；
- Mock 与 API 使用同一 Repository 接口和领域类型；
- 首页、动态难题、详情、快讯、证据库和方法页均有独立路由；
- 正常、加载、空、部分失败、过期和错误场景均可演示；
- 趋势变化和证据之间可以下钻；
- 所有 Mock 页面明确标记为演示数据；
- 桌面、平板和手机主要流程可用；
- 支持键盘操作和减少动效；
- 单元、组件和核心 E2E 测试通过；
- 静态构建结果可以继续由当前 `dist` 托管；
- 技术实现与产品文档没有未记录的偏差。
