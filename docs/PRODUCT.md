# 大模型求职与研究雷达：MVP 产品文档

## 1. 文档目的

本文档是项目开发、数据设计和验收的主要依据。MVP 先验证一件事：能否持续从可信来源中发现大模型行业正在出现的真实难题，并把这些信号转化为程序员可执行的求职和研究建议。

## 2. 产品定位

产品暂定名为“大模型求职与研究雷达”。

它不是通用 AI 新闻聚合站，也不是预先列好若干热门方向的导航站。产品通过持续采集招聘、产业、工程实践和研究证据，动态生成以下答案：

1. 最近市场正在关注哪些大模型问题？
2. 哪些问题正在升温，哪些只是短期讨论？
3. 企业为解决这些问题需要哪些岗位和能力？
4. 程序员下一步值得学习、研究或制作什么作品集？

## 3. 目标用户

MVP 优先服务以下用户：

- 希望进入大模型行业的在校生和应届生；
- 希望转向 AI 应用开发的后端、前端、数据和平台工程师；
- 正在选择作品集或研究方向的开发者；
- 希望判断 AI Native 与传统行业 AI 机会的求职者。

## 4. 核心原则

### 4.1 难题必须动态发现

“Agent 记忆”“工具调用稳定性”“评测”“企业 RAG”“长程任务”等只作为第一批种子标签，用于冷启动和验证流程，不是固定导航栏目，也不是永久分类。

系统应允许新的问题根据证据自动出现，并允许旧问题被合并、拆分、改名、降温或归档。首页展示的是当前数据窗口内得分较高的问题，而不是写死的五个方向。

### 4.2 证据优先

每个趋势、统计和建议必须能回到原始来源。系统需要保存来源链接、发布者、发布日期、抓取时间、证据片段、内容校验状态和适用地区。

抓取失败、只有标题、受到登录限制或无法验证正文的页面可以保留为线索，但不能计入趋势统计和结论。

### 4.3 区分事实、推断和建议

- 事实：来源中明确出现的招聘要求、数据或工程问题；
- 推断：系统根据多条证据归纳出的趋势；
- 建议：根据趋势为程序员生成的学习或项目方向。

页面上必须让用户知道一条内容属于哪一层，不能把模型总结包装成来源原话。

### 4.4 小样本不冒充全市场

MVP 使用定向来源样本，只能描述“当前样本中的证据强弱和变化”，不能宣称为整体市场份额。岗位数量、薪资和技能占比必须同时显示样本量、时间窗口和数据来源。

## 5. MVP 用户故事

### 5.1 查看今日信号

用户打开首页，可以看到最近更新的权威资讯、招聘变化和新出现的问题，并能区分新增、升温和持续关注。

### 5.2 查看动态难题

用户可以浏览系统自动归纳的问题列表。每个问题至少显示：

- 问题名称和一句话定义；
- 当前热度和趋势方向；
- 支持该问题的有效证据数；
- 最近首次和最后出现时间；
- 涉及的行业、岗位和技能；
- 代表性证据；
- 为什么值得程序员关注。

### 5.3 查看证据

用户进入问题详情页后，可以查看形成该结论的原始证据，并按来源类型、地区、时间和验证状态筛选。

### 5.4 获得行动建议

每个问题提供一份简短指导：

- 更适合哪类程序员；
- 建议补齐的能力；
- 可制作的最小作品集；
- 可以量化的验收指标；
- 传统行业 AI 或 AI Native 的适用场景。

## 6. MVP 页面范围

### 6.1 首页

- 产品定位和最后更新时间；
- 最近 7 天新增或变化最大的动态问题；
- 最新权威资讯与招聘信号；
- 当前样本概况：有效来源数、验证率、地区和来源类型分布；
- 数据口径与免责声明入口。

### 6.2 动态难题列表

- 按趋势得分排序；
- 支持时间窗口、地区、行业和来源类型筛选；
- 展示升温、稳定、降温、新出现等状态；
- 不依赖固定的前端分类枚举。

### 6.3 难题详情

- 动态生成的问题定义；
- 趋势变化和证据构成；
- 相关岗位与技能；
- 原始证据列表；
- 面向程序员的学习、研究和作品集建议；
- 相近问题和可能的上下位关系。

### 6.4 证据库

- 展示全部来源及验证状态；
- 支持按发布者、来源类型、地区、日期和问题筛选；
- 可以打开原文；
- 清楚标记无法验证正文的线索。

MVP 暂不建设账号系统、社区评论、付费课程、简历自动生成、职位投递和个性化推荐账户。

## 7. 数据来源

MVP 优先接入少量但稳定、可信且可验证的来源：

1. 政府、公共就业服务和权威研究机构；
2. 企业官方招聘页和招聘平台公开岗位；
3. 企业工程博客、官方技术报告和公开复盘；
4. 论文、Benchmark 和研究机构报告；
5. GitHub 等公开开发生态数据；
6. 主流媒体报道，仅作为补充或线索。

每个来源需要记录来源等级。单篇媒体报道或单个岗位不能独立形成高置信趋势。

## 8. 动态问题生成流程

### 8.1 采集与验证

定时读取来源目录，抓取正文并保存 HTTP 状态、抓取时间、内容摘要、校验哈希和短证据片段。

### 8.2 信息抽取

从每条有效证据中抽取：

- 明确描述的问题或瓶颈；
- 岗位名称与技能；
- 行业、业务场景和地区；
- 可量化的数据；
- 来源所提出的解决方向。

### 8.3 问题归并

系统将语义接近的问题归并成候选主题，同时保留原始表述。归并需要满足：

- 能解释各条证据的共同问题；
- 不把过于宽泛的“AI 落地难”当作有效问题；
- 可以追踪别名和名称变化；
- 低置信聚类进入待审核区，不直接进入首页。

### 8.4 趋势评分

MVP 趋势得分至少考虑：

- 有效证据数量；
- 独立发布者数量；
- 来源类型多样性；
- 招聘、生产实践和研究是否交叉支持；
- 时间新鲜度；
- 与上一观察窗口相比的变化；
- 来源可信度。

不得仅按文章数量排名。单一发布者集中发布多篇内容时应降低重复贡献。

### 8.5 建议生成

只有达到最低证据阈值的问题才生成求职建议。建议必须引用相关证据，并分别输出“观察到的需求”“推断”“建议行动”。

## 10. 更新策略

MVP 先支持手动运行数据管线，并为以后定时更新预留接口。目标节奏为：

- 资讯和招聘信号：每日或每周更新；
- 趋势评分：每次有新数据后重新计算；
- 周报：每周生成一次；
- 问题定义和建议：证据发生显著变化时重新生成。

所有页面显示数据截至时间，不承诺伪实时更新。

## 11. MVP 验收标准

### 数据可信

- 所有计入统计的证据正文均通过验证；
- 每个高置信问题至少由两个独立发布者支持；
- 趋势页可以回溯到原始证据；
- 页面显示样本量、时间窗口和更新时间。

### 动态发现

- 新问题可以只通过新增数据和管线生成，无需修改前端代码；
- 初始五个种子问题可以被新问题替换或重新排序；
- 问题支持新增、升温、稳定、降温和归档状态；
- 相似证据不会简单重复计数。

### 用户价值

- 用户能在首页判断本周值得关注的三个方向；
- 每个高置信问题至少提供一个可执行作品集建议；
- 建议包含可测量的验收指标，而不是只列技术名词；
- 用户可以在两次点击内从结论到达原始来源。

### 工程质量

- 数据统计来自可重跑管线，不在前端手填；
- 管线失败不会覆盖上一版可用数据；
- API 与页面对空数据、抓取失败和未知分类有明确处理；
- 项目自带验证命令能够检查主要数据约束。

## 12. 开发优先级

### P0：完成可验证的动态闭环

1. 扩展数据模型，取消固定问题枚举依赖；
2. 实现证据抽取与候选问题归并；
3. 实现可解释的趋势评分；
4. 改造首页和问题详情以读取动态数据；
5. 确保所有结论可追溯到证据。

### P1：增强求职价值

1. 抽取岗位、技能、行业和地区；
2. 增加岗位技能统计；
3. 为动态问题生成作品集与学习建议；
4. 生成每周变化摘要。

### P2：扩大覆盖与个性化

1. 增加更多合规数据源；
2. 加入用户背景和方向匹配；
3. 增加订阅、提醒和历史趋势对比。

## 13. 当前版本约定

现有五类问题和已有证据继续作为 MVP 冷启动数据使用，避免第一版重做全部内容。但后续实现必须逐步将它们从静态定义迁移为管线生成的数据。

在动态抽取和聚类能力完成以前，页面应明确标记当前为“种子问题样本”，不能让用户误以为系统已经覆盖全部市场问题。
